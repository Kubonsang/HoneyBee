# v0.7 workspace-only migration

HoneyBee v0.7 intentionally breaks compatibility with its orchestration/control-plane product.

## Removed surface

- Run, DAG, Journal, approval, Agent session, Unity execution, verified patch, publish, merge, and
  provider-specific integration commands and modules.
- `workspace launch` and tool configuration.
- `@honeybee/control-plane-contracts` and `@honeybee/orchestration-contracts`.
- Desktop Agent Manager, setup/control plane, Run review, approval, patch disposition, and integration
  IPC and UI.
- The native Agent host and executable orchestration dogfood harnesses.

Historical benchmark, validation, architecture, and ADR evidence is unchanged. Removed code remains
available in Git history at the v0.6/baseline commits.

## Registry migration

The active file is `workspace-registry-v2.json`. On first use, Core can read a v1 registry only when
every cache and Workspace already carries the ADR-031 `library-only-v1` and
`git-worktree-library-cow-v1` markers. The next mutation writes validated v2 data. The v1 file is left
untouched as rollback evidence.

Full-project records fail closed with `registry.layout-unsupported`; v0.7 never guesses that their
paths or storage ownership match the Library-only layout.

## Upgrade sequence

1. Stop HoneyBee Desktop and any command that mutates the registry.
2. Preserve the HoneyBee application-data directory and record `git worktree list --porcelain` for
   every registered repository.
3. Build/install v0.7 and run `honeybee project list --json` and `honeybee workspace list --json`.
4. Resolve any Full-project records with the version that created them; then re-register and prepare
   a Library-only cache in v0.7.
5. Verify every clean Workspace with `workspace status --json`. Do not remove dirty Workspaces.
6. Run focused create/work/remove validation. After a reboot, wait for `repair-required`, run
   `workspace repair`, and verify `ready` before opening the Workspace.

## Rollback

Before any v0.7 mutation, restore the copied application-data directory and the prior binary. After a
v0.7 write, stop all HoneyBee processes and retain `workspace-registry-v2.json` for diagnosis; the
untouched v1 registry is the rollback reference. Never point an older binary at v2 by renaming the
file.

Workspace branches and authored files are independent of the registry and must not be deleted during
rollback. If lifecycle state is uncertain, preserve the worktree and VHDX and investigate rather
than forcing cleanup.

## Verification and rollback by stage

| Stage               | Required verification                                                      | Rollback boundary                                           |
| ------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Package cleanup     | typecheck, build, dependency graph, absence of legacy imports              | restore prior commit; no user data changed                  |
| Registry v2         | parser migration and concurrent atomic-update tests                        | stop writers; restore app-data copy or untouched v1         |
| CLI                 | help/JSON contract tests; removed commands fail                            | use prior CLI against its matching registry copy            |
| Desktop             | strict IPC typecheck, production build, renderer smoke, PTY smoke          | use CLI; Desktop has no independent state                   |
| Workspace lifecycle | real Git worktree create/status/dirty refusal/retry/remove; branch remains | preserve branch/worktree/storage, retry from recorded state |
| Reboot repair       | elevated physical reboot gate from ADR-031; explicit repair returns ready  | on failure, keep the retained Child intact for diagnosis    |
